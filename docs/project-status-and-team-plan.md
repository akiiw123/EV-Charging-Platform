# 充电桩应用管理平台：项目现状、问题与后续分工

> 文档日期：2026-09-01  
> 评估基线：`main` 分支，提交 `e97cf50`  
> 唯一开发目录：`/home/bit/charging-platform`  
> 远程仓库：<https://github.com/QLang423/charging-platform>

## 1. 文档目的

本文依据《东软电动汽车充电桩应用管理平台》项目说明书和当前仓库代码，对项目完成度进行可验证的盘点，并给出后续 5 人小组分工。文中状态定义如下：

- **已实现**：已有可运行代码，且主要流程能够在 Ubuntu 虚拟机中验证。
- **部分实现**：已有基础能力，但未达到说明书描述的完整交互或质量要求。
- **未实现**：仓库中尚无对应的有效业务实现，或仅有占位说明。

## 2. 当前系统结构

```text
Qt 用户端 ────── TCP/JSON ──────┐
                                │
Qt 运营管理端 ── TCP/JSON ──────┼── Qt TCP 服务 ── SQLite
                                │
Web 运营大屏 ─── HTTP/JSON ─────┘   （当前由只读 Python 服务直接查询数据库）

机器学习模块：仅预留目录，尚未接入业务链路
```

当前技术栈：Ubuntu、C++17、Qt 6 Widgets、Qt Network、Qt SQL、Qt Charts、SQLite、Python 标准库 HTTP 服务、ECharts。

## 3. 已实现功能

### 3.1 工程、构建与版本管理

- 已建立 GitHub 仓库并配置 SSH 推送，主分支为 `main`。
- 已建立 CMake 多模块工程，划分用户端、管理端、核心库、测试、大屏和机器学习目录。
- 已提供数据库建表脚本、演示数据和自动初始化逻辑。
- 已提供开发构建目录 `build/dev`，用户端和管理端均可在 Ubuntu 中编译运行。
- 已配置 `.gitignore`，数据库、构建产物、IDE 文件和 Python 缓存不会进入仓库。
- 当前有 3 个自动化测试程序：协议与密码测试、仓储测试、TCP 集成测试。

### 3.2 数据库与核心仓储层

- 用户、管理员、充电站、充电桩、充电订单 5 类核心数据已建表。
- 用户手机号和电桩编号有唯一约束。
- 用户和电桩均通过部分唯一索引限制只能存在一个活动订单。
- 已实现用户查询/自动注册、资料修改、充值、冻结/解冻。
- 已实现充电站查询和新增、电桩查询/新增/状态更新。
- 已实现预约、开始充电、停止充电、结算、取消预约和历史订单查询。
- 预约、开始、停止和结算的关键状态变更使用数据库事务。
- SQLite `CURRENT_TIMESTAMP` 按 UTC 存储，C++ 展示层已转换为本地时间，已修复固定多出 8 小时的问题。

### 3.3 TCP 通信与并发服务

- 已实现“一行一条 JSON”的 TCP 请求/响应协议，并复用请求 ID。
- 管理端默认监听 `0.0.0.0:45454`，用户端可通过环境变量指定服务地址和端口。
- 已实现客户端断线后每 2 秒自动重连。
- 服务端采用受限线程池，每个连接任务独立创建 SQLite 连接，避免数据库连接跨线程共享。
- 单条消息限制为 1 MiB；无效 JSON、未知请求和业务错误均返回结构化错误码。
- 用户身份和管理员身份绑定 TCP 连接，业务接口不接受客户端任意指定用户 ID。

### 3.4 Qt 用户端

- 支持输入 11 位手机号免密登录；新手机号自动创建用户，默认昵称为“用户+手机号后 4 位”。
- 登录后展示昵称、手机号和钱包余额。
- 支持修改昵称和头像路径，支持模拟钱包充值。
- 支持查看全部充电站，展示站名、地址、价格、总桩数和空闲桩数。
- 支持点击电站查看电桩编号、快慢充类型、功率和状态。
- 支持完整的“预约 → 开始充电 → 停止充电 → 钱包结算”流程。
- 支持取消尚未开始的预约，支持查看最近 50 条订单。
- 充电时实时展示计时、预计电量和预计金额。
- 开始/停止充电后会重新读取电站和电桩状态；已修复界面仍显示 `idle` 的问题。
- 用户存在活动订单时，服务端会阻止创建第二个订单，客户端会加载现有订单。

### 3.5 Qt 运营管理端

- 支持管理员账号密码登录，默认演示账号为 `admin / 123456`。
- 旧数据库首次成功登录后，会把开发占位密码自动升级为带随机盐、120,000 次迭代的 PBKDF2-SHA256 哈希。
- 运营总览展示今日、本月和累计营收，以及空闲、充电中、故障、离线电桩数量。
- 使用 Qt Charts 展示近 30 日营收折线趋势。
- 支持充电站列表、新增电站，并按数量批量初始化电桩。
- 支持查看所有电桩的编号、所属站点、类型、功率、状态、累计次数和累计时长。
- 支持模拟远程重启非充电状态的电桩。
- 支持按手机号模糊查询用户并冻结/解冻账号。

### 3.6 Web 运营数据大屏

- 已实现可独立启动的 Python HTTP 服务，不需要安装额外 Python 包。
- 提供 `/api/dashboard` 只读 JSON 接口。
- ECharts 页面展示今日营收、在线电桩、进行中订单、近 7 日营收和电桩状态分布。
- 页面每 5 秒刷新一次，最近 7 日无营收日期会补 0。
- Web 统计已按服务器本地时区处理日期边界。
- 可在 Windows 浏览器通过 `http://192.168.179.128:8080` 查看虚拟机实际数据。

### 3.7 自动化验证

- 覆盖消息编解码、手机号注册登录、资料修改、钱包充值和电站/电桩查询。
- 覆盖订单事务、余额不足回滚和完整 TCP 充电流程。
- 覆盖开始充电后电桩变为 `charging`、停止后恢复 `idle`。
- 覆盖充电开始时间与当前时间一致，不再出现固定 8 小时偏差。
- 覆盖管理员错误密码、登录、电站新增、电桩查询、用户查询和权限校验。
- 覆盖 PBKDF2 哈希生成、正确/错误密码校验、畸形哈希拒绝和旧密码自动升级。

## 4. 部分实现的功能

### 4.1 附近充电站

当前只能展示数据库中的全部电站和电桩详情。尚未实现用户当前位置、区域选择、地址输入、地址转经纬度、距离计算、按距离排序和距离显示，因此还不能称为完整的“附近充电站查询”。

### 4.2 用户信息维护

昵称和余额功能已经可用；头像目前只是保存一个文本路径，没有文件选择器、图片预览、默认灰色头像、格式/大小校验或上传机制。

### 4.3 未完成订单引导

服务端能够识别活动订单并拒绝重复预约，用户端也会读取活动订单；但尚未实现说明书要求的弹窗提示与强制跳转到专门的订单结算页面。

### 4.4 销售业绩图表

管理端有 30 日折线图和三项营收指标，但没有 7 日/30 日切换，横轴未展示真实日期，缺少悬浮提示和更完整的图表样式。

### 4.5 电桩状态统计

管理端显示各状态数量，但没有按说明书展示占比百分比；也没有故障告警列表或状态筛选。

### 4.6 充电站与充电桩管理

新增站点和模拟重启已经可用，但尚未支持编辑/删除站点、单独新增/编辑电桩、手工切换故障/离线状态。站点列表显示空闲数，但未直接显示在线率百分比；点击站点行也不会自动过滤站内电桩。

### 4.7 错误处理

协议层和大部分业务层已有错误码、事务和参数检查，但 GUI 多数错误只在状态栏短暂显示，缺少确认对话框、字段级提示、重试状态和统一日志。尚未形成说明书要求的“完整错误处理机制”。

### 4.8 大数据可视化

当前大屏属于基础实时运营看板，完成了少量核心指标；尚未形成“数据采集、预处理、分析、模型部署”的完整数据链路，也没有站点排行、时段分布、利用率、地图分布或预测结果。

## 6. 当前存在的问题与风险

### P0：演示前必须处理

1. **管理端营收日期仍有 UTC 边界问题**：Web 大屏已使用 `date(created_at,'localtime')`，但 Qt 管理端统计 SQL 仍直接使用 `date(created_at)`，北京时间凌晨可能把收入归到前一天。
2. **开发数据库存在一个活动订单**：当前实际数据库统计曾显示 `active_orders = 1`。演示前应检查该订单属于预约、充电中还是待结算，并通过正常业务流程处理，不能直接删库掩盖问题。
3. **默认管理员密码仍公开**：数据库会自动升级为哈希，但默认口令仍是 `123456`，且 `must_change_password` 只返回给客户端，没有真正的强制改密页面和接口。
4. **Web 服务直接读取 SQLite**：课程演示可用，但与架构文档“通过统计接口访问”的边界不完全一致；并发写入时可能出现短暂锁等待，也暴露了数据库文件路径。

### P1：核心需求缺口

1. 附近站点、距离排序、腾讯地图和导航完全缺失，是说明书中用户端最主要的未完成需求。
2. 机器学习负荷预测完全缺失，是四大子系统之一的明显缺口。
3. 活动订单没有弹窗和强制结算引导，用户可能不理解按钮为何不可用。
4. 管理端图表没有 7/30 日切换，状态统计没有百分比。
5. 头像功能只有路径文本，不符合“选择图片并展示头像”的预期。

### P2：质量与可维护性问题

1. 请求路由、SQL 和大量业务规则集中在单个 `request_router.cpp` 中，继续扩展容易产生冲突，应拆分用户、订单、管理和统计服务。
2. 部分管理端 SQL 直接写在路由层，仓储边界不一致，统计逻辑在 Qt 服务和 Python 大屏中重复。
3. 充电电量按“电桩额定功率 × 时间”模拟，且最少按 `0.01 kWh` 计量；适合演示，但不代表真实充电曲线。
4. 金额使用 `double` 存储和计算，可能有浮点误差；正式业务应改为整数分或定点数。
5. 预约没有超时释放机制，长期未开始的预约会一直占用用户和电桩的活动订单唯一索引。
6. 用户被冻结后，已经建立且已登录的 TCP 会话不会立即失效；冻结只会阻止后续重新登录。
7. 客户端发出并发请求后仅按响应类型处理，没有利用请求 ID 建立回调映射；复杂页面可能出现旧响应覆盖新状态。
8. TCP 没有 TLS、会话令牌、心跳、速率限制和服务端空闲连接超时。
9. Python 大屏服务依赖 CDN 加载 ECharts；虚拟机或 Windows 无法访问互联网时，图表无法渲染。
10. 当前 `CMakePresets.json` 的版本高于虚拟机现有 CMake 可识别版本，`cmake --preset dev` 会失败；目前只能使用显式 `cmake -S . -B build/dev`。
11. 测试主要覆盖核心层和 TCP，缺少 Qt GUI 自动化、Web API 单元测试、并发压力、数据库迁移和异常断线测试。
12. 用户端与管理端主要采用代码创建界面，视觉层次、输入校验提示、空状态和可访问性仍较基础。

## 8. 协作方式与分支建议

- 每人从最新 `main` 建立短期分支：`feat/user-map`、`feat/admin-ops`、`feat/ml-dashboard`、`test/ci-release`；组长使用 `fix/core-services`。
- 一个 PR 只解决一个主题，禁止把格式化全仓库与业务修改混在同一 PR。
- 接口变更顺序：先更新协议文档和测试，再改服务端，最后由客户端接入。
- 数据库结构变更必须新增迁移版本，不允许要求成员删除已有数据库重新开始。
- 每个 PR 至少由一名非作者评审；核心业务和数据库变更由组长及测试负责人共同评审。
- 每天合并前同步 `main`，解决冲突后重新跑测试；不直接向 `main` 强制推送。
- 地图 Key、密码和部署地址通过环境变量或未跟踪的本地配置注入，严禁提交真实密钥。

## 12. 总结

项目目前已经具备可运行的用户充电闭环、运营管理基础功能、SQLite 数据层、TCP 多线程通信和实时 Web 看板，可以作为阶段性演示版本。与项目说明书相比，最大缺口是地图导航和机器学习子系统；最大工程风险是统计口径重复、预约不超时、默认账号改密未闭环、测试与部署自动化不足。后续应先稳定已有业务，再并行推进地图、管理端完善、机器学习大屏和测试发布工作。
