## 1. 项目概述

本项目面向电动汽车充电服务场景，建设一个由用户端、运营管理端、核心业务服务、SQLite 数据库、Web 运营大屏和智能负荷预测服务组成的应用管理平台。

当前阶段已经打通“用户登录 → 查询电站 → 预约电桩 → 开始充电 → 停止充电 → 钱包结算 → 订单查询”的核心业务闭环，同时具备电站、电桩、用户、订单和营收的运营管理能力。地图导航、Web 数据展示和机器学习预测均已有代码实现和界面入口。

中期答辩应将项目定位为：**核心功能可运行、主要子系统已集成、正在进入联调验收和质量收口阶段**，不应表述为已经完成生产级交付。

## 2. 当前系统架构

```text
Qt Quick/QML 用户端 ─────┐
                         ├── TCP + JSON ── Qt/C++ 管理服务端 ── SQLite
Qt Quick/QML 管理端 ─────┘                     │
                                               ├── Web 运营大屏
                                               └── Python 预测服务（HTTP/JSON）

腾讯地图 Web API ── Qt WebEngine ── 用户端地图与路线规划
```

主要技术栈：

- C++17、CMake 3.21+、Qt 6.2。
- Qt Quick/QML、Qt Quick Controls 2、Qt WebEngineQuick。
- Qt Network、TCP 长连接、一行一条 JSON 消息协议。
- SQLite、Repository、事务和数据库约束。
- Python、PyTorch、独立 HTTP/JSON 推理服务。
- Python 标准库 HTTP 服务、ECharts Web 运营大屏。

项目保持清晰的职责边界：QML 负责界面和交互，C++ Controller 负责状态与业务编排，核心库负责数据库、协议和业务规则，Python 服务独立完成训练与推理。

## 4. 已完成的具体内容

### 4.1 核心服务、数据库与通信

已完成：

- 建立用户、管理员、充电站、充电桩、订单、充值记录、计价规则和分时价格段等数据表。
- 使用唯一索引限制同一用户和同一电桩同时只能存在一个活动订单。
- 实现手机号免密登录和首次登录自动注册。
- 实现预约、开始充电、停止充电、取消预约、钱包充值、结算和订单历史。
- 开始充电后电桩切换为 `charging`，停止或取消后恢复正确状态。
- 关键订单与钱包操作使用数据库事务，避免部分写入。
- 实现管理员登录、密码哈希升级和修改密码接口。
- 实现用户冻结；已登录用户被冻结后会被服务端强制下线。
- 实现电站新增、编辑、逻辑停用/恢复以及受外键保护的删除。
- 实现电桩新增、编辑、状态切换和模拟重启；充电中禁止危险操作。
- 实现预约超时释放、重复结算提示和越权操作校验。
- TCP 服务支持多个客户端同时在线，默认容量为 64，可通过环境变量调整。
- 单条 TCP 消息限制为 1 MiB，无效 JSON 和业务错误返回结构化错误码。
- 客户端按请求 ID 和发送序号丢弃同类型旧响应，降低异步响应覆盖新状态的风险。
- 新增数据库完整性检查、在线备份、备份校验和恢复能力。

计价模块已具备固定电价、分时电价规则和占位费计算能力。当前实际订单结算仍沿用固定电价；分时电价与占位费尚未正式接入订单扣费，这是答辩时需要主动说明的边界。

### 4.2 Qt 用户端

用户端已完成 Qt Quick/QML 移动端重构，设计基准约为 440×820，并适配最低约 390×680。

已完成页面与功能：

- 手机号登录、首次自动注册和登录错误反馈。
- 首页、电站列表、站点搜索、筛选、距离显示和排序。
- 六个内置城市的模拟定位；配置腾讯地图 Key 后可对任意地址进行地理编码。
- 电站详情和电桩列表，展示快慢充、功率与状态。
- 预约、开始充电、实时计时、停止、取消和钱包结算。
- 活动订单检测与未完成订单处理引导。
- 订单历史和充值记录。
- 昵称修改、头像选择、图片校验、裁剪保存和持久化。
- 青绿、信号蓝、云白蓝、翡翠绿等主题切换与偏好保存。
- 驾车/步行导航，通过 Qt WebEngine 打开腾讯地图路线规划。
- 5 秒轮询刷新，使管理端和多个用户端之间的数据近实时同步。
- 中文输入、右键复制粘贴、触控板与鼠标滚轮适配。

当前边界：

- 内置城市属于模拟定位，不等同于真实 GPS。
- 任意地址解析和腾讯地图依赖 `TENCENT_MAP_KEY` 及网络。
- 地图运行依赖 Ubuntu 的 `libqt6webenginecore6-bin`。
- 同步方式为约 5 秒轮询，并非服务端实时推送。

### 4.3 Qt 运营管理端

管理端已完成 Qt Quick/QML 宽屏桌面重构，适配 1440×900，最低窗口为 1280×720。

已完成页面与功能：

- 管理员登录、首登改密提醒、密码修改和登录状态管理。
- 数据总览：今日、本月、累计营收，完成订单数，平均订单金额，注册用户数，电桩状态和在线率。
- 近 7 日/30 日营收趋势切换，连续日期补零和空数据提示。
- 电站管理：搜索、区域匹配、新增、编辑、逻辑停用/恢复、删除确认和站内电桩详情。
- 电桩管理：搜索筛选、新增、编辑、状态切换和模拟重启。
- 订单管理：订单列表、搜索、状态筛选和详情查看。
- 用户管理：手机号搜索、状态筛选、冻结/解冻及强制下线说明。
- 智能预测：请求 Python `/stations` 和 `/predict` 接口，展示未来 1/6/24 小时负荷、预计空闲桩和风险状态。
- 设置：七套主题、侧栏状态、动画开关、字体缩放和页大小持久化。
- 表格使用 C++ 列表模型，支持滚动、加载、空数据和失败状态。
- 危险操作提供明确目标的二次确认，并在异步期间防止重复提交。

当前边界：

- 数据库没有电桩心跳时间字段，页面只能明确显示“暂无心跳字段”。
- 数据库没有独立的电站更新时间字段。
- 服务端分页协议尚未实现，目前主要是客户端筛选和有限条数返回。
- 删除有历史订单关联的电站会被外键规则拒绝。

### 4.5 机器学习与智能预测

`ml` 目录已不再是空占位，当前包含：

- `data.py`：统一加载“站点 × 小时”时序数据。
- `export.py`：从平台 SQLite 只读导出脱敏站点级训练数据。
- `model.py`：负荷预测模型定义。
- `train.py`：训练、验证、早停和指标输出。
- `service.py`：独立 JSON HTTP 推理服务。
- `requirements.txt`：Python 依赖。

预测服务提供：

- `GET /health`：服务和模型状态。
- `GET /stations`：可预测站点列表。
- `POST /predict`：未来 1/6/24 小时负荷、90% 区间、24 小时曲线和预计空闲桩。

管理端已经接入上述服务。服务或模型不可用时，页面会明确显示“演示数据”或失败状态，不把模拟值伪装为真实预测。

当前边界：

- 自有平台历史数据量可能不足，建议积累至少四周再训练正式模型。
- 中期重点证明数据格式、训练流程、服务契约和界面接入；最终答辩前还需补充真实模型指标、对比实验和模型产物验收。
- 预测服务不直接修改订单、电桩或用户数据，只提供辅助决策结果。

### 4.6 自动测试与工程质量

当前 CMake 注册了七个自动测试程序：

1. `core-tests`：消息协议、密码与核心工具。
2. `repository-tests`：Repository 和订单数据操作。
3. `tcp-integration-tests`：真实 TCP、鉴权、充电流程、管理操作和并发。
4. `pricing-tests`：固定/分时计价、占位费和规则事务。
5. `database-maintenance-tests`：备份、校验、恢复和完整性检查。
6. `database-robustness-tests`：错误数据、写入失败、并发和较大数据量。
7. `display-time-tests`：UTC 与北京时间显示边界。

2026-09-07 在 Ubuntu 22.04、Qt 6.2.4 环境中的实际结果：

- CMake 配置通过。
- 用户端、管理端、核心库和全部测试目标构建通过。
- 7 个 CTest 程序中 6 个通过。
- `tcp-integration-tests` 中 19 个用例通过，`reconnectAfterInitialRefusal` 稳定失败。

因此答辩时应表述为“主要自动测试通过，首次连接被拒后的自动重连仍有一个已知缺陷”，不能表述为全部测试通过。

### 5.2 真实限制

- 当前 TCP 协议未启用 TLS，没有正式会话令牌和速率限制。
- 金额仍使用浮点数，正式系统应改用整数分或定点数。
- Web 服务直接读取 SQLite，适合演示但不是最终服务边界。
- 电桩没有真实硬件心跳或设备遥测数据。
- 充电电量按功率与时间估算，不等同于真实充电曲线。
- 地图、任意地址解析和模型训练均依赖外部配置或数据，答辩前必须准备降级方案。

  → 用户端登录并预约
  → 管理端看到电桩状态变化
  → 用户端开始/停止/结算

## 9. 建议回答口径

### 为什么项目完成度不是 100%？

中期阶段已经完成核心闭环和主要子系统，但真实模型效果、生产安全、服务端分页、自动部署和一个重连缺陷仍需完成。当前重点是证明架构成立、数据链路打通、关键业务可验证。

### 项目的主要技术难点是什么？

主要难点不是页面数量，而是多个客户端共享同一业务状态：预约与充电需要事务和唯一约束，用户冻结需要影响现有连接，异步响应需要避免旧数据覆盖新状态，地图和预测还涉及 Qt 与外部服务的跨技术栈集成。

### 项目的创新或特色是什么？

- 用户端、运营管理端、Web 大屏和预测服务形成完整链路。
- 核心状态由服务端统一维护，避免客户端伪造业务结果。
- 预测服务与 Qt 解耦，可替换数据集和模型而不改 GUI。
- 具备数据库备份恢复、并发预约、异常回滚和多层自动测试，不只是静态演示页面。

### 下一阶段最重要的目标是什么？

先修复自动重连并完成全系统联调，再用真实数据训练和评价模型，随后接入完整计价规则、补服务端分页、CI 和可重复部署脚本，最终形成稳定演示版本与答辩材料。

## 10. 中期结论

项目当前已经具备可运行的用户充电闭环、运营管理能力、数据大屏和智能预测技术链路。数据库约束、服务端业务规则和自动测试为系统可靠性提供了基础。中期后的重点不再是继续堆叠页面，而是解决已知缺陷、完成真实模型评估、统一数据口径并提升部署和演示稳定性。
