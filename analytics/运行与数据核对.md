# 最新总项目 ZIP5：分析与接口整合修复版

本包基于你上传的 `EV-Charging-Platform-main (5).zip`。原 ZIP 未修改，最新 Vue3/DataV 大屏、Qt 业务端和 3460 个 OSM 地图站点保留。不是只替换一个 Python 文件：分析输出、Spark SQL、导出、MySQL 导入、接口和前端来源提示需要一起更新。

## 你的分析体现在哪里

统一入口是 `analytics/scripts/evcharging_analysis.py`，负责原始 CSV → ODS → DWD 清洗/去重/关联 → DWS → 10 张 ADS。原来的嵌套入口转发到这个脚本；原代码留在 `analytics/docs/evcharging_analysis_original.py.txt`。

| Spark/MySQL 表 | `/api/v1/dashboard` 的 data 字段 |
|---|---|
| ads_kpi_overview | overview |
| ads_user_level_dist | user_levels |
| ads_user_radar | user_radar |
| ads_platform_dist | platforms |
| ads_hour_trend | hour_trend |
| ads_station_type_eff | station_types |
| ads_week_compare | week_compare |
| ads_battery_health | battery_health |
| ads_area_cost | area_costs |
| ads_station_topn | top_stations |

字段顺序、类型、可空字段在 `analytics/ads_contract.json`。ADS 为 `ncs_ads` 下的 Parquet 表，新建数据库默认 HDFS 位置为 `/evcharging/warehouse/ncs_ads`，不是旧 `/evcharging/ads/daily_orders` 等目录。已有 Hive 数据库仍使用原 LOCATION，需先用 `DESCRIBE DATABASE EXTENDED ncs_ads` 确认。旧 ADS 不删除，但新接口不读取它们。

大屏的全国地图来自独立静态站点清单，并不能证明 Spark 分析接通。证明需要同时检查：大屏分析来源、导出 manifest、MySQL 导入批次、10 组接口数值一致。新增核对工具可逐字段比较。

## 运行前条件

你截图的 Hadoop 机器有 Hadoop 3.3.0、Spark 3.4.1、Java 8，但 Python 只有 3.10.13。课堂要求 3.11/3.12，因此还需要准备 Python 3.11。不要直接使用不存在的 `/opt/module/3.11/bin/python3.11`。Spark 3.4.x 在本包配 Python 3.11；Python 3.12 配 Spark 3.5.x，不能混用。所有 Spark worker 使用一致 Python 环境。本包默认 local[*]，先在单机验证，之后再配置集群。

bitdev 截图没有运行 MySQL、没有 API 环境，因此仅解压后打开浏览器不会自动启动完整系统。先确定龙云 MySQL 实际所在机器、用户名/密码和 API 机器 IP。不要使用未确认的示例 IP。后端 Python 3.11/3.12，MySQL 8.x，前端 Node >=23（建议现有 Node24）。Spark 3.4.1 的 Java 支持见 [官方运行说明](https://dlcdn.apache.org/spark/docs/3.4.1/)；无需为本修复盲目重装 Java。

把项目复制到虚拟机本地用户目录的新文件夹后运行，例如 `~/evcharging-integrated-zip5`。不要在 `/mnt/hgfs` 内创建虚拟环境或 Derby/Hive metastore。以下命令均在 Linux 终端执行，路径占位符必须替换。

## 1. Hadoop 机器：准备环境和原始数据

进入本地项目的 analytics 目录，确认 `command -v python3.11` 有真实输出后执行：

```bash
python3.11 -m venv .venv
.venv/bin/python -m pip install -r requirements-spark.txt
export SPARK_SUBMIT=/opt/module/spark-3.4.1/bin/spark-submit
export HADOOP_CONF_DIR=/opt/module/hadoop-3.3.0/etc/hadoop
export PATH=/opt/module/hadoop-3.3.0/bin:$PATH
hdfs getconf -confKey fs.defaultFS
hdfs dfs -ls /evcharging/raw/orders
hdfs dfs -ls /evcharging/raw/stations
hdfs dfs -ls /evcharging/raw/piles
hdfs dfs -ls /evcharging/raw/users
```

确保 Hadoop/HDFS 正在运行，fs.defaultFS 指向实际 NameNode。四个必需文件：

```text
/evcharging/raw/orders/charging_orders.csv
/evcharging/raw/stations/charging_stations.csv
/evcharging/raw/piles/charging_piles.csv
/evcharging/raw/users/users.csv
```

原始订单表头需要 id、user_id、pile_id、status、created_at、started_at、ended_at、energy_kwh、amount；站点需要 id、name、address；桩需要 id、station_id、type；用户需要 id。不要把已有正确 CSV 重复上传。如果需要重新从业务 SQLite 只读导出：

```bash
.venv/bin/python scripts/export_business_csv.py --db /实际位置/业务数据库.db --out runtime/raw_csv
bash scripts/upload_raw.sh runtime/raw_csv
```

平台 `platform`、起始电量 `soc`、区域 `city` 有真实字段才统计；缺平台/SOC 时对应面板提示缺数据，不补造。缺 city 归入未知区域。

## 2. Hadoop 机器：分析并导出

仍在 analytics 目录：

```bash
export COST_PER_KWH=0.6
bash scripts/export_ads_local.sh --analyze
.venv/bin/python scripts/import_ads_mysql.py --dir runtime/ads_export --validate-only
```

成功后 `runtime/ads_export` 有 10 个无表头、竖线分隔 CSV 和 manifest.json。所有清洗、DWS、ADS、导出在一次流程完成；不要同时直接运行另一份分析脚本。失败就停止，不导入旧数据。单独导出会检查分析成功状态、脚本版本和原始数据是否变化。运行工作目录保持一致，避免默认 Derby metastore 分裂。

## 3. MySQL 机器：建表并导入

将整份 `runtime/ads_export` 复制到运行 MySQL 的机器本地项目 `analytics/runtime/ads_export`。不要仅复制单个 CSV。若 MySQL 位于远端，也可在获授权且网络可达的导入机器使用相应 ETL 凭据；默认脚本创建的 ETL 账号只供 MySQL 本机使用。

MySQL 安装和服务启动由实际数据库机器负责。在该机器 analytics 目录：

```bash
python3.11 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
bash scripts/bootstrap_mysql_users.sh
set -a
source .secrets/analytics-etl.env
set +a
bash scripts/import_ads_mysql.sh --dir runtime/ads_export
```

bootstrap 创建/迁移 charging_ads 的分析表，创建只读 API 用户和写入 ETL 用户，会重置这两个专用账号的随机密码。只在首次部署或明确需要轮换时执行，先保留已有分析库备份；不改 Qt 业务表。它默认使用本机 MySQL root 登录，若 root 仅支持系统 socket 管理员认证，需用已授权的管理账号运行；非默认端口需先核对客户端连接配置。不要把 `.secrets`、`.env` 或业务数据库传 GitHub。

导入先校验全部文件、字段、数值、键、校验和及汇总关系，再在一个事务内替换 10 张结果表和批次来源；导入失败保留上一批。

## 4. Flask/API 机器：启动接口

后端使用龙云实际 MySQL 地址及只读 API 凭据。MySQL 与 Flask 同机时直接使用刚生成的文件；异机时把私密配置安全放到 API 机器，修改 MYSQL_HOST 为数据库机器真实 IP，并确保访问已允许。进入 API 机器本地项目 analytics 目录：

```bash
python3.11 -m venv .venv
.venv/bin/python -m pip install -r requirements.txt
export ANALYTICS_ENV_FILE="$PWD/.secrets/analytics-api.env"
bash scripts/start_api.sh
```

保持终端运行。默认监听 `0.0.0.0:8091`，可通过 ANALYTICS_BIND 更改。浏览器先打开 `http://API机器实际IP:8091/api/v1/health`，再打开 `/api/v1/dashboard`。health 只证明数据库连接；dashboard 顶层 metadata 应含 batch_id、analysis、quality、tables，不只是有图表数据。

## 5. 前端机器：构建并打开大屏

进入本地项目 `web/dashboard`：

```bash
node --version
npm ci
npm test
npm run build
```

建议前后端使用同一份本地项目目录：构建产生 `web/dashboard/dist` 后，Flask 托管它，打开 `http://API机器实际IP:8091/dashboard/`。项目包不附带 dist 和 node_modules，因此必须构建。若构建在另一台机器，把 dist 完整放到 Flask 项目对应位置或设置 DASHBOARD_DIST_DIR。

开发预览可用 `ANALYTICS_PROXY_TARGET=http://API机器实际IP:8091 npm run dev`，打开 `http://前端机器实际IP:5173/dashboard/`。地址末尾保留斜杠。代理默认127.0.0.1只有前后端同机才正确。API 位于另一台虚拟机时先验证网络连通。

## 6. 直接证明接口用了这批分析

在含有相同导出目录的机器、analytics 目录运行（Python 标准库，无需 curl）：

```bash
.venv/bin/python scripts/verify_chain.py --dir runtime/ads_export --base-url http://API机器实际IP:8091
```

只有显示 `PASS: all ten API groups equal the Spark export` 才说明此次接口 10 组数据与本地 Spark 导出逐字段一致，且 API 的分析来源、输入质量、文件校验和、生成时间匹配，脚本版本也匹配本包。这是运行链路核对，不是防恶意伪造的密码学证明。数据更新后须重新运行，不能拿旧 PASS 代表新批次。

大屏新增分析批次、生成时间、原始/有效/剔除订单数及可展开脚本来源。页面“最近读取”仅表示浏览器请求时间，不能当作 Spark 更新时间。

## 口径与验证范围

充电会话仅计 charging/awaiting_payment/completed；营收仅计 completed 的 amount+occupancy_fee；剔除比例包含清洗、去重和关联失败。相对负载不是时长利用率；SOC 不是电池健康诊断；成本按 COST_PER_KWH 估算；工作日不处理法定节假日和调休。无差异雷达维度为 null，前端明确提示无法完整归一化。

本次 11 项 Python 离线测试、6 项前端 Node 测试通过；检查 Python、JavaScript 和 Vue script 部分语法。SQL 算术测试使用人工样例和 SQLite 兼容适配，MySQL 事务使用模拟连接，不是实际 Hadoop/MySQL 联调。此环境没有可用 Spark/MySQL 服务、Flask 或 Vue 构建依赖；依赖下载被自动审批策略拒绝，因此没有宣称真实 Flask 测试、npm build、浏览器端到端或完整运行通过。请按上面的顺序在你们实际机器完成最终验证。
